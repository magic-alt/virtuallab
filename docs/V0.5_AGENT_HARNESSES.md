# V0.5 — Agent workspace and multi-harness adapter

VirtualLab remains an independent, local-first engineering workbench. No named user project, hardware laboratory, firmware board or external application repository is a dependency.

## Feature scope

- Agents tab bound to the active workspace/worktree, separate from GitHub/Terminal/Run/Review
- One active native harness owner per workspace, with persisted provider-specific thread bindings
- A bounded, **ephemeral** 300-event structured timeline; no persistent chat/evidence registry
- Editable generic role prompts, plus opt-in locally defined skills; both are plain text, not executables
- Manual Connect/Resume, Start turn, Interrupt, Stop runtime and Forget thread operations
- Optional safety approval record and typed external lease-provider contract, **no bundled hardware provider**

The main project invariant is unchanged: **the Workspace owns the Agent, not the other way around**.

## Harness transports

| Adapter identity | Native transport | Session continuity | Steering | Default permission policy |
| --- | --- | --- | --- | --- |
| Codex | \`codex app-server --listen stdio://\` JSON-RPC | app-server thread IDs | Supported | \`workspace-write\` / \`approvalPolicy: never\` |
| DeepSeek | Codex app-server + DeepSeek Responses provider | app-server thread IDs | Supported | Same as Codex, no approval auto-escalation |
| Claude Code | \`claude -p --verbose --output-format stream-json --permission-mode plan\` | CLI session ID from structured events, resume with \`--resume\` | No live steer | Plan mode; backend controls still apply |
| OpenCode | \`opencode run --format json --agent plan\` | CLI session ID from JSON events, resume with \`--session\` | No live steer | Plan agent; backend controls still apply |

The CLI path uses direct native executables, not shell command strings or TUI scraping. On Windows the Claude/OpenCode command must resolve to a native executable on PATH; VirtualLab does not execute \`.cmd\` shims with a user prompt. Provider/version flags should be validated on the target machine.

Provider-side plan/permission controls are not an OS sandbox. Treat unknown CLI plugins, hooks and workspace instructions as untrusted. Run outside real hardware environments unless a separate physical safety solution is implemented.

## DeepSeek adapter

DeepSeek is a real, explicit provider identity in the UI and persisted binding. It is NOT just a prompt prefix or a simulated response. The native bridge uses the already supported Codex app-server Responses protocol and explicitly passes:

- provider = \`deepseek\`
- base URL = \`https://api.deepseek.com\`
- API protocol = \`responses\`
- model = \`deepseek-flash\`
- credential via environment variable \`DEEPSEEK_API_KEY\`

VirtualLab does not display, serialize or save the key, nor does it edit \`~/.codex/config.toml\` or model metadata. Users must install Codex and configure the official DeepSeek Codex model catalog themselves. See [DeepSeek's official Codex setup guide](https://api-docs.deepseek.com/quick_start/agent_integrations/codex/) and [Responses API guide](https://api-docs.deepseek.com/guides/responses_api/). The model catalog may need future revisions when upstream model IDs change.

Example PowerShell, for the current terminal session **only** (do not commit or paste keys into logs):

\`\`\`powershell
$env:DEEPSEEK_API_KEY = Read-Host "DeepSeek API key"
npm run tauri:dev
\`\`\`

The desktop process must inherit the key; a separately launched packaged executable must inherit it from its launcher environment. Availability reports unavailable when the key or Codex CLI is missing. API connectivity and billing are controlled by the external provider; no live API call is made during basic capability detection.

## Agent event flow

\`\`\`text
Selected workspace
   ├─ persisted harness/thread binding
   ├─ role + selected skills -> prompted turn
   └─ typed HarnessAdapter
       ├─ Codex/DeepSeek: stdio JSON-RPC
       └─ Claude/OpenCode: non-interactive NDJSON
                 ↓
          Tauri agent://event
                 ↓
         filtered workspace timeline
\`\`\`

A CLI thread starts with a provisional ID and upgrades only when a provider-native session ID appears in the local structured event stream. A failed CLI executable or unsupported version can fail without a resumable native session; this is visible as an error. Interruption kills the top-level CLI subprocess but is not process-tree containment.

## Protected operations and lease boundary

The front-end approval broker accepts a direct human acknowledgement, a short-lived scoped request and a single consumption attempt. **This is a record, not permission to actuate hardware.** It cannot forge a hardware lease, unlock a flash tool or approve a GitHub release.

The \`EnforcingHardwareProvider\` contract requires an independent trusted service capable of acquiring, validating before each operation and releasing scoped leases. The built-in provider is \`null\` and all \`authorize\` operations reject. The preexisting private Rust \`HardwareBroker\` is likewise not exposed as a public grant issuance command.

Before offering real hardware actions, an optional provider must implement independent resource registration, out-of-band human authentication, watchdog/e-stop, interlocks, safe-state on TTL expiry and crash, operation-scoped audit provenance and hardware-side permission checks. Software-only approvals cannot be represented as an accepted physical safety gate.

## Verification

Automated: \`npm ci && npm run typecheck && npm test && npm run build\`, plus \`cargo test --locked\`, \`cargo check --locked\`, and \`npm run acceptance:local\` on supported hosts.

Manual: review the [V0.5 control acceptance checklist](./CONTROL_ACCEPTANCE.md#v05--agent-workspace-control-acceptance) for each provider and a packaged Windows build. CI cannot validate external provider authentication, real DeepSeek billing/model inference, or a device-side interlock.
