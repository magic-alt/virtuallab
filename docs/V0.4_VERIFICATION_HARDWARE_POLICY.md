# V0.4 Verification Runner, Evidence Store and Hardware Policy

This slice extends the V0.4/V0.5 foundation already merged via #10. It is intentionally developed on a new branch based on that merge commit, **not** on the historical V0.3 branch.

All verification runs and hardware metadata are scoped to the repository/workspace selected by the user. No external project repository, hardware ID, board path, or lab adapter is installed, imported, or assumed by default.

## Native verification runner

Tauri commands:

- `verification_run`: accepts `{runId, workspaceRoot, profile}`; validates the Git worktree HEAD, profile schema and safe run/gate identifiers.
- `verification_cancel`: sets an active-run cancellation token; a running child process receives a termination request.
- `verification_import_artifact`: imports a JUnit/trace/VCD/image/report file, but only from within the workspace.

Only explicit process gates of kind `build`, `unit`, or `evidence` with `approval: none` can run. Initial commands are restricted to direct build/test tool executables. HIL, hardware and soak gates and adapter executors always return **BLOCKED**. This **is not** a sandbox and does not make untrusted build scripts safe to execute. Verification profiles must come from a trusted operator or controlled repository policy and are not exposed as arbitrary agent commands.

The subprocess runner uses typed executable + argument vectors, per-gate timeouts (at most ten minutes), cancellation, and independent stdout/stderr capture. Process termination is best-effort; killing the top-level process is **not** a hard guarantee of terminating its process tree. Do not treat cancellation as a physical emergency stop.

## Evidence storage

Local evidence is ignored by Git and stored in:

```text
<workspace>/.virtuallab/evidence/<run-id>/
  profile.json
  manifest.json
  <gate-id>.stdout.log
  <gate-id>.stderr.log
  import-N-<filename>    # optional JUnit / VCD / CSV / reports
```

The manifest records the full Git HEAD SHA, normalized per-gate result, run time, and SHA-256 + size of recorded artifacts. Run identifiers reject traversal and evidence paths reject pre-existing symlink directories. Artifact imports resolve their source inside the active workspace. Runs use new directories and refuse to overwrite an existing run ID.

Known limitations: the first runner exposes only a single-workspace process gate path, no fully atomic manifest update or process-tree supervision, and no versioned immutable artifact registry. The safe follow-up is to harden atomicity, detached-process handling and per-run trust provenance before enabling Agent-controlled execution.

## Native hardware lease/approval policy

The Rust `HardwareBroker` is a **private in-process policy contract**. It defines:

- L0 metadata inspect; L1 workspace build; L2 read-only bench; L3 motion/power/flash; L4 release
- registered resource capabilities
- `shared-read` / `exclusive` leases with TTL (max ten minutes)
- conflict avoidance and expired-lease cleanup
- scoped, expiring, one-use human grants
- denial of missing, replayed, expired or agent-issued approvals

Crucially, **there is no public Tauri method to mint a human approval or arm hardware**, and no hardware backend accepts these software lease objects yet. The TypeScript `evaluateHardwarePolicy` is only a UI preview, never an authorization authority. Agent code cannot grant itself higher permissions.

Software lease expiry/release is not a fail-safe stop of an energized DUT. Any optional hardware provider must independently enforce hardware watchdog, interlocks, emergency-stop, safe-state restoration and independent authorization on every physical action.

## Test gates

- TypeScript tests: policy levels, grant scope/expiry, lease collision, blocked/cancelled evidence verdict
- Rust tests: SHA-256 log hash, run ID traversal guard, blocked required HIL verdict, lease TTL/conflict/one-use grant, anti-escalation
- Existing Linux/macOS/Windows desktop acceptance and frontend Node 22/26 CI

## Deferred production gates

- trusted profile source and executable/argument restriction policy
- real operator approval UI and one-use capability token minting
- capability verification performed independently by any explicitly installed, project-neutral hardware provider
- OS process-tree termination and crash recovery
- independent resource monitoring / hardware watchdog in any optional provider
- artifact atomicity + retention + manifest signature
